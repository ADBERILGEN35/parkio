# New Relic budget ledger recovery guard (source-only preparation)

`scripts/newrelic_log_pilot/budget_gate.py` now supports `PARKIO_NR_BUDGET_RECOVERY_MODE=on`. The default is `off`; normal first installation still creates `budget.db` and initializes the configured limits. Invalid flag values fail startup. This PR does **not** set the flag in a unit, env file, Compose file or production system.

## Guarded startup and runtime behavior

With the flag `on`, the gate requires a pre-existing, regular, readable and writable SQLite file at `PARKIO_NR_BUDGET_STATE_DB`. It opens with SQLite `mode=rw`, checks integrity and the complete budget schema, requires the single accounting row and exact configured total/daily/monthly limits, verifies nonnegative counters and requires the persistent `exhausted=1` bit prepared by the operational-state snapshot workflow in draft PR #101. It checks that a write transaction can start. It does not create a parent directory, database, table, row or replacement ledger in this mode. Missing, unreadable, corrupt, incomplete, mismatched or nonexhausted state fails before the HTTP listener starts. A symlink is rejected.

While guarded, the real `Budget.reserve()` cannot admit a batch even if a counter rolls over; `/health` remains failed. With a valid exhausted ledger, `/log/v1` retains the existing exhausted-budget response (202 with `accepted=false`), which can acknowledge and drop incoming logs. **Keep Fluent Bit stopped throughout the hold** to avoid that loss. The gate rechecks the ledger file identity before and after each database operation. If the file disappears, is replaced, becomes unreadable or loses the exhausted bit while running, `/health` and `/log/v1` return 503 and no new upstream request is made. It never falls back to SQLite's create-if-missing open. The check covers requests after detection; an already in-flight upstream attempt cannot be recalled. Stop the collector before manipulating the ledger and treat such attempts as unknown spending. The test-control reset endpoint cannot clear an active recovery guard.

The guard enforces a **closed hold**, not a decision that spending has been reconciled. A valid `budget.db` at the actual container bind path is essential. Setting only an environment flag without installing that exact verified file makes startup fail. PR #101's staged archive is an offline input, not an active runtime interlock.

## Future integration and explicit release

No production action is authorized by this document. A later approved integration should:

1. Keep the source helper and Fluent Bit collector stopped. Verify the separately restored source/collector state, PR #101 snapshot identity and checksum, and the exact `budget.db` bind path before starting the gate. Do not infer a live file's existence from repository configuration.
2. Stage the PR #101 ledger with `exhausted=1`, verify SQLite integrity/schema and file ownership/permissions, enable `PARKIO_NR_BUDGET_RECOVERY_MODE=on` in the dedicated gate's configuration, and prove startup fails for a missing mount. The gate can then run in a closed state for inspection, with the collector still stopped.
3. Reconcile **all** possible post-snapshot New Relic attempts, including unknown outcomes and attempts spanning UTC day/month boundaries, against independent evidence. If usage has no defensible upper bound or remaining headroom cannot be proved, keep `exhausted=1`, the guard on, and forwarding disabled. No automatic day/month reset authorizes a release.
4. For a separately approved release, stop the gate again. Preserve the original exhausted ledger and its checksum. On an isolated copy, record the reviewed accounting adjustment and current-period limits/counters; clear `exhausted` only when the total and applicable day/month budgets still have verified headroom. Recheck integrity, schema, exact limits and checksum. Install that reviewed file at the verified bind path. Only then switch recovery mode `off`, preflight that the ledger still exists at that path, start the gate, inspect `/stats` and `/health`, and start the collector/source helper under the separately approved runbook. Normal mode still permits an intentional first install if the file is missing, so a later coordinator must enforce the preflight at this transition.
5. If the release preflight or startup fails, keep the collector stopped, return to the preserved exhausted ledger and `on` mode, and investigate; never use a fresh empty ledger as rollback. If an attempt may already have reached New Relic, count it conservatively before trying again.

This PR does not provide an accounting adjustment command or authorize manual SQL changes on a real ledger. That decision and isolated restore drill belong to the later production integration. No real New Relic calls, backup, restore, restart or production configuration changes were made.
