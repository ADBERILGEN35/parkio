# FAQ Structure

The landing page FAQ should answer the highest-friction questions near the end of the page. It should not replace the full startup FAQ.

## Recommended Order

1. What is Parkio?
2. Is Parkio live?
3. What cities are supported?
4. How does spot verification work?
5. Does Parkio track my location?
6. What is Smart Return?
7. Is Parkio free?
8. What data is stored?
9. Can I delete my data?
10. Is Parkio public-production ready?

## Answer Intent

### What is Parkio?

Use the canonical one-line description.

### Is Parkio live?

State:

> Parkio is currently in release-candidate and hosted-beta preparation. The public production service is not live yet.

### What cities are supported?

State:

> Supported beta areas are TBD.

Do not list cities until confirmed.

### How does spot verification work?

Explain that availability signals can be shared, verified, claimed, or reported by the community. Avoid implying perfect accuracy.

### Does Parkio track my location?

Keep the answer tied to implementation evidence. If precise product behavior is not finalized for the public beta, say so.

Recommended language:

> Parkio is designed to be privacy-conscious. Public beta data collection details will be documented before launch.

### What is Smart Return?

Explain it as a product feature that helps drivers manage return context and reminders after parking. Do not overstate automation.

### Is Parkio free?

State:

> Beta monetization is not active. Future pricing is TBD.

### What data is stored?

Keep answer high-level and link to the privacy policy when available.

### Can I delete my data?

Use an honest implementation-aware answer. If deletion workflow is not documented for public beta, state:

> Account and data deletion handling for public beta is TBD.

### Is Parkio public-production ready?

State:

> No. Parkio is technically mature for hosted-beta preparation, but public production readiness still requires deployment, operating history, privacy/legal publication, support processes, and real-world beta validation.

## FAQ Writing Rules

- Keep each answer under 80 words where possible.
- Use plain language.
- Do not introduce new product claims.
- Link to technical or startup docs for deeper evidence.
- Avoid legal certainty unless reviewed.

## Optional Expanded FAQ Categories

For a separate FAQ page, group questions by:

- Product
- Beta Status
- Privacy and Safety
- Verification and Trust
- Technology
- Data and Account
- Startup and Contact
